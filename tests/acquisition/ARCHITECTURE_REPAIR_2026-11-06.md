# 采集架构修复与再评估

日期：2026-11-06。范围：修复只读评估中确认的数据交付语义、配置生效可观测性、手动/自动仲裁及路线定义分散问题；本次不加入连续振动采集。

## 实施约束

- 特征缓存保持按需发布；原始振动和声音发布必须检查 Buffer 及实际数据通道，未交付不得报告成功。
- 用户配置与批次快照分离，使用配置版本及已应用版本表达异步生效；状态读取不等待串口。
- 手动请求由后台线程执行，调用者同步等待完成；定长振动窗口在批次之间允许声音插入，保留窗口统计和配置快照。
- 每条路线最多一个手动请求，避免无界积压；信号取消在途请求时等待安全收尾，停止时完成等待者。
- 路线名称、模式映射、能力条件、时长及执行方法集中定义；连接状态与采集路线分开。
- 共用的收尾分派与静默等待移出振动专属实现，保留有限批次的只读恢复门禁。
- 保留用户既有未提交内容；仅在项目内构建，不安装到 NFS 或加载开发板模块。

### 调用与并发契约

主机配置写入只取短状态锁。版本仅在实际值修改时增加；工作线程复制配置、配置轮询策略并
更新已应用版本。模式/时长/路线变化重启窗口，长度和轮询变化不重启。
显式手动振动窗口沿用提交时的配置；该窗口期间新配置保持 pending，窗口完成后应用。
版本相等表示配置已被调度接纳，不承诺已有新数据；判断实际工作应同时检查 route/busy。

手动请求每条路线最多一个（包括正在执行的请求），重复提交返回 EBUSY。
工作线程在批次间公平仲裁请求；声音使用振动窗口的墙钟时间，不延长窗口，
若声音结束时振动窗口已过期，不再额外启动振动批次。窗口统计仍首批重置、后续累计。

排队请求被信号取消时不发送触发命令；在途请求先安全收尾，再返回 EINTR。
调用者等待完成后才释放栈上的请求，避免工作线程保留悬空指针。卸载、恢复失败、
升级暂停均完成等待者。有同步采集请求时，波特率查询/修改、传感器参数写入及固件升级
返回 EBUSY，避免在显式窗口中改变配置或写 Flash；主机调度配置仍可短锁保存。

IIO Buffer 代次在开启、关闭回调中更新，不获取采集锁。发布、代次检查、通道检查均短持
IIO mlock；采集等待不持 mlock。即使 Buffer 在两个发布调用之间关闭并重启，也会使本批失败。
交付失败与串口失联分别处理，不因 IIO 丢样扫描波特率。

### 架构再评估

**当前结构适合现有三路线的特征与定长采集，职责边界总体合理，可以继续作为开发基础。**
声音已使用与振动相同的工作线程、请求完成、交付检查和恢复入口；手动调用不再自建采集循环。
连接状态、采集路线、用户配置及实际配置具有各自的状态归属，用户态可以观察待生效配置。
新的同类定长功能可以沿路线描述、型号回调和对应 IIO 接口扩展，修改位置比先前集中。

本次不实现连续流。当前描述明确区分 snapshot 与 finite_batch，有限批次仍依靠自然结束、
静默及只读恢复；未来连续振动必须实现自身的开始/运行/主动停止/停止确认/恢复生命周期，
并核对停止命令在流状态下的发送和确认、卸载及 OTA 顺序、序号回绕、时间语义及持续带宽。
不能把循环定长采集当成无间断波形，也不能仅增加一个模式枚举便承诺连续采集。

剩余验收重点是 XYZ/XYZS 实板上的 Buffer 切换、请求取消、三路线轮转、断线恢复与长时间通信。
应分设备记录 UART 错误、内核日志增量、超时恢复和数据完整性；当前没有新增实机证据。
